# Jamdani v6 — sealed opening and host-addressed guests

19 October 2026, Asia/Dhaka. Latest user correction supersedes the earlier skip/auto-open rules: the entire invitation must remain concealed until the guest explicitly opens it. Template/product first; storefront and multi-order implementation are deferred.

## Implemented corrections

1. **Real opening gate:** event/date/photo/RSVP/wish/footer chapters and navigation are conditionally unmounted while closed or opening. Cover text for the inner card is inert and hidden from accessibility before completion. There is no pre-open “View details”, chapter shortcut or auto-opening RSVP fragment.
2. **Accessible deliberate entry:** normal seal click opens in about 1.8 seconds. Quiet opening is still an explicit guest action. Reduced/missing motion APIs do not open the invitation automatically. OS preference change or pause can finish an opening already initiated by the guest; pausing a closed invitation does not reveal it. Repeated taps do not restart the timer. Fragment navigation is honored only after opening.
3. **A named welcome:** host-created recipient name appears on the cover, custom localized greeting inside, and recipient identity on the response leaf. The cover names the couple as sender and avoids repeating the recipient name in redundant greeting lines. Optional Bengali name/English greeting/message fields preserve old saved data through fallbacks.
4. **No guest name form:** RSVP and private wishes use the host-created household identity. No household is created by a guest reply. The isolated public sample is now addressed to Sabbir & Family / সাব্বির ও পরিবার. General share links are view-only, with a message directing replies to personal links. Unknown/blank/ambiguous guest scope does not fall back to another household.
5. **Response refinements:** reception remains the primary cover/reply event even if programme entries are reordered. A single permitted event has no unnecessary dropdown. Existing drafts/deadline/allowance/edit/storage feedback remain. Error/receipt focus uses immediate, bounded scrolling. A repeated private-wish submission cannot create another wish until an explicit “write another” action.
6. **Presentation/animation:** responsive personal cover, coordinated theme colours, normal text wrapping, delayed chapter navigation after the cover, and decorative petals paused when the cover is offscreen or page is hidden. Photo lightbox selection follows photo identity through reorders, closes on removal and retries a replacement source after an earlier failure.
7. **Host-side glue only:** the existing guest dialog now supports localized names/greetings/messages and editing an existing personal invitation while preserving its ID/link and replies. It prevents lowering the party limit below retained accepted attendance. This was not a redesign or implementation of the production multi-order dashboard.

## Remaining release limits

This is a frontend refinement, not a claim that every possible frontend/device or commercial gate is passed. Physical iPhone/Android, WhatsApp/Facebook browser, real keyboard/safe areas, 200% OS text scaling, measured frame rate/LCP/INP/CLS, slow-network/low-memory qualification and the complete content/TE matrix remain required. Backend/shared data, per-wedding security, idempotency/conflict handling, upload processing and hosted deployment remain outside this pass. UI opening is presentation state, never an authorization mechanism.
